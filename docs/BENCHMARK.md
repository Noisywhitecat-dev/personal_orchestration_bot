# 동일 과제로 비교하는 AI 개발 실험

## 추천 과제: 회의실 예약 보드

외부 API·로그인·결제 없이 React + TypeScript로 만드는 단일 화면 앱이다.
단순 CRUD에 예약 충돌 규칙과 저장 복원을 더해 구현 정확도, 예외 처리, UI와 테스트를 함께 평가한다.
처음부터 앱을 세 개 만들기보다 같은 준비된 Vite/React/TypeScript/Vitest 시작 커밋을 세 폴더로 복제한다.
폴더 사이에는 코드·대화·메모리를 공유하지 않는다. 이번 작업에서는 비교 실험을 실행하지 않았다.

### 공통 범위

- 회의실은 A/B/C 세 개로 고정. 예약: 제목, 회의실, 날짜, 시작·종료 시각.
- 날짜는 YYYY-MM-DD, 시각은 HH:mm. 한 예약은 같은 날 안에 있고 시작 < 종료.
- 같은 회의실·날짜의 예약 구간은 겹칠 수 없다. 끝과 다음 시작이 같은 인접 예약은 허용한다.
- 수정 시 자기 자신의 기존 예약은 충돌 비교에서 제외한다.
- 예약 생성·수정·삭제, 날짜/회의실 필터, 시간순 목록과 해당 날짜의 예약 수.
- localStorage 저장 및 새로 고침 복원. 잘못된 저장 데이터는 오류를 알리고 자동 덮어쓰지 않는다.
- 빈 상태·입력 오류·좁은 화면·키보드 조작. 라이브러리 없는 CSS로 충분하다.
- 반복 예약, 사용자 관리, 서버, 실시간 동기화, 알림, 달력 라이브러리, 드래그 앤 드롭은 제외한다.

## 모델과 노력치

첫 비교는 비용과 비교 가능성을 우선해 아래처럼 고정하는 것을 권한다. 성능 보장이나 실측 결과가 아니다.

| 조건            | 모델                                             | 노력치      | 작업 방식                                     |
| --------------- | ------------------------------------------------ | ----------- | --------------------------------------------- |
| Claude 단독     | claude-sonnet-4-6                                | medium      | 계획·구현·자체 검증                           |
| Codex 단독      | gpt-5.6-terra                                    | medium      | 계획·구현·자체 검증                           |
| AI orchestrator | Claude: claude-sonnet-4-6 / Codex: gpt-5.6-terra | 각각 medium | Claude 계획 → 승인 → Codex 구현 → Claude 검토 |

별칭 sonnet 대신 명시 모델을 사용해 실험 도중 대상이 바뀌는 일을 줄인다.
이 앱의 고급 설정에서 두 모델과 노력치를 개별 지정한다. 계정에서 선택할 수 없다면 세 조건 모두의 기준을 먼저 다시 고정한다.
협업 조건에서만 상위 모델을 사용하면 협업 효과와 모델 성능 차이를 구분할 수 없다.
medium은 양사에서 동일한 추론량을 뜻하지 않으므로, 같은 노력치 이름이 동일 비용이라는 가정도 하지 않는다.

첫 결과가 부족할 때만 동일 설정으로 실패 항목을 재확인한다. 두 번째 실험에서 Claude와 Codex를 각각 high로 올리되 단독/협업 양쪽을 함께 바꾼다.
처음부터 Astra/Opus 최고 노력치를 쓰면 작은 과제에서 비용 차이가 커져 협업 효과를 보기 어렵다.
더 강한 모델끼리의 별도 비교가 필요하면 Claude Opus와 GPT-5.6 Sol을 명시 버전·동일 조건으로 새 묶음에서 비교한다.

근거: [Codex 모델 안내](https://learn.chatgpt.com/docs/models)는 Terra를 일상 작업의 균형 모델로 설명하며 높은 노력치의 시간·토큰 증가를 안내한다.
[Claude 모델·노력치 안내](https://code.claude.com/docs/en/model-config)는 Sonnet 4.6의 medium을 지원하고 비용을 줄이는 설정으로 설명한다.
제품별 실제 계정 접근 가능 여부는 별도다.

## 실행 상한

- 조건별 벽시계 시간은 25분을 권장한다. 조건을 시작한 뒤 요구사항을 추가하지 않는다.
- 단독은 최초 작업 요청 1회와 같은 세션의 공통 체크리스트 검토/수정 1회까지 허용한다.
- 협업은 질문 0회, 검토 최대 2회, Claude 최대 3회, Codex 최대 2회로 설정한다.
- 협업의 최소 호출은 계획+구현+검토 3회, 수정 1회가 필요하면 총 5회다. 내부 도구 호출·모델 턴 수와는 다르다.
- 추가 질문이 없도록 아래 요구사항을 완성해서 전달한다. 답이 없는 부분은 합리적 가정을 기록한다.
- 출력은 변경 파일, 실행한 검증, 남은 실패를 짧게 보고하도록 제한한다.
- 작업당 Claude 20,000 / Codex 40,000 토큰을 초기 경계값으로 둘 수 있다. 이는 소비 예상치가 아니다.
  이 앱의 한도는 다음 실행 전에 적용하므로 진행 중인 한 번의 호출을 정확히 끊는 하드 한도가 아니다.
  단독 도구에 동일한 한도 강제가 없으면 이를 실험 조건 차이로 기록하고 사후에 공통 예산 이내 결과도 비교한다.
- 실제 CLI 호출 승인과 폴더 준비는 실행 시 별도로 한다. 본 문서는 실행 지시가 아니다.

## 공통 요청문

> 제공된 React/TypeScript 시작 프로젝트에서 회의실 예약 보드를 구현하라.
> 이 문서의 공통 범위를 수용 조건으로 사용한다. 추가 의존성·서버·외부 API·새 에이전트를 사용하지 말라.
> 관련 파일부터 확인하고 구현·관련 테스트·typecheck·build를 완료하라.
> 예약 충돌 판정은 UI와 분리하고, 인접 구간 허용 및 자기 자신을 제외한 수정 검사를 테스트하라.
> 저장 데이터가 손상되었을 때 기존 원문을 자동 덮어쓰지 말라.
> 범위를 넓히지 말고 마지막에 변경 파일, 검증 명령과 결과, 미완료 항목을 간단히 보고하라.

## 평가

AI가 쓴 테스트의 개수나 자기평가로 순위를 정하지 않는다. 세 결과를 A/B/C로 가리고 동일한 검증을 적용한다.
가능하면 구현 전에 평가용 테스트를 만들어 세 구현에 그대로 적용하고, 각 구현의 자체 테스트와 분리한다.

| 항목        | 배점 | 확인 내용                                                             |
| ----------- | ---- | --------------------------------------------------------------------- |
| 기능·정확성 | 60   | CRUD·필터·순서·검증·충돌·자기 제외 수정·저장 복원·손상 데이터 보호    |
| 검증과 구조 | 20   | 경계값 테스트, 실행 가능한 명령, 로직과 UI 분리, 불필요한 의존성 없음 |
| 사용성      | 20   | 입력 오류의 위치, 키보드, 작은 화면, 빈 상태, 일관된 기본 동작        |

필수 경계 사례: 동일 구간, 일부 겹침, 완전 포함, 인접 구간, 다른 회의실,
다른 날짜, 역전 시각, 자기 자신 수정, 타 예약으로 겹치게 수정, 삭제 후 재예약,
새로 고침 복원, JSON 손상, 유효 JSON이지만 잘못된 스키마, 필터 후 편집, 560px 화면.

완성도와 효율은 별도 표로 기록한다. 점수만 높고 추가 수정이 많으면 효율이 좋은 결과라고 보지 않는다.
기록할 값: 최초 결과 점수, 최종 점수, 첫 완성까지 시간, 전체 시간, 사용자 개입 수,
Claude/Codex 각각 보고한 입력·캐시 입력·출력·추론 토큰, 호출 수, 검증 실패 항목.
미보고 usage는 확인 불가로 남기고 토큰을 추정하지 않는다. 서로 다른 제공자의 토큰 수를 같은 가격으로 합산하지 않는다.
5시간/주간 한도 변화율은 다른 작업도 포함하고 과금 단위와 다를 수 있으므로 효율 점수로 쓰지 않는다.
Claude 비대화형 작업은 계정의 Agent SDK 크레딧 체계가 적용될 수 있으므로 구독 한도만으로 비용을 판단하지 않는다.
[Claude 비대화형 실행 안내](https://code.claude.com/docs/en/headless)

처음은 세 조건을 한 번씩만 실행해 비용을 확인한다. 한 번의 결과는 예비 비교이며 모델 우열의 증거가 아니다.
결과 차이가 의미 있고 비용을 감당할 수 있을 때만 새 폴더에서 각 조건을 2회 더 반복한다.
